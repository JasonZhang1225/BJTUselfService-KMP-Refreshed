# 课程回放四平台审查标准与后续工作

更新：2026-10-28。适用分支：`feat/courseware-fallback-playback`。

本文以 Windows 已通过的课程回放验收为基准，统一 Android、iOS、macOS、Windows 的结果、证据和收尾标准。统一的是用户能完成的事情与数据正确性，不强制四端使用相同播放器、后台机制或文件路径。

本轮授权：Windows 标记完成并提交推送；编写四端标准及后续计划。Android P0/P1 和 Apple 真机工作是后续任务，本次不执行 ADB、安装、优化、合并主干或发布。

状态按以下含义使用：

- **已实现**：源码存在，不等于已运行。
- **测试通过**：写明单元/fixture/硬件/真实服务器/用户确认中的哪一类。
- **平台完成**：该平台实际支持的流程已验收，列清设备、包版本、已知限制与例外。
- **四端完成**：四端均有对应证据；Windows 的成绩不能替代其他平台。
- **发布就绪**：另需最终构建矩阵、安装/签名、版本号、主干与发布审批；不由“平台完成”自动推出。

当前状态以 `memory.md` 和本文件为准；`playback-android-performance.md` 的原分析及 `playback-composite-android-windows.md` 的旧报告只作历史与候选方案参考。若出现新实测与旧推断冲突，保留证据并更正当前结论。

Windows 完成范围包含 NVIDIA 本机真实使用与压力测试、已有 AMD 验证、保存入口和预览修复。Intel 真机、CPU 纯软件整节、多小时耐久测试未验证；Windows 中断合成后保留下载分片、继续时重新合成，是已明确的能力边界，不宣称保留编码进度。用户已要求停止网卡测速差异排查。

## 3. 媒体正确性与性能口径

### 3.1 每次整节都必须核对

1. 记录输入指纹、两路时长/帧率/轨道、合成档位和时间轴规则；单路无损保存与双路重编码分开验收。
2. 合成输出应为选择档位的 H.264、25 fps；按显示时间检查视频 PTS 无重复/缺口，相邻间隔 40000 μs，帧数与约定时间轴一致。若有 B 帧，分别检查显示次序的 PTS、解码次序的 DTS 和 `ctts`，不能把合法重排当丢帧。
3. 同一标准样本沿用 175564 视频帧、7022.56 秒的既有基线；**其他课节另算，禁止硬编码该数或强行裁到相同帧数**。单路转封装保留源时间轴，不强制改成 25 fps。
4. 检查 AAC 配置、采样率、声道、样本数、时间戳和样本字节哈希。先剥离容器/ADTS 等封装，再用同一种方法计算顺序 AAC 样本哈希；MP4 文件哈希不同不能证明声音被改过。
5. AAC 原样复制是 Windows/Android 对照标准。源音轨已有的起止偏差要记录；比较新增的音画偏差和持续漂移，不能要求本来不同长的两条源轨强行等长。
6. 检查首/中/尾、分段连接点和恢复边界画面，核对左右、方向、黑边、裁剪及尾帧；实际播放检查音画对应。整个输出执行 `ffmpeg -v error -xerror -i <output.mp4> -f null -`，退出 0 才算完整解码通过。
7. 中断后的成片与不中断基线比较帧数、时间轴、AAC 和画面内容；不同硬件编码器的有损视频文件不要求二进制相同，但不能增加丢帧、裁剪或明显画质损失。

**已知 iOS 差距**：`AppleVideoCompositor.kt` 当前将声音读为 PCM，再编码为 48 kHz 双声道 AAC；不能通过与 Windows 同等的“原样 AAC 哈希”标准。iOS P0 必须量化该差距；后续接入 AAC 直通，或取得用户针对该差异的明确接受并写明例外，不能默认为四端一致。macOS helper 当前使用压缩音频读写，仍须实测样本哈希，不能只凭 `outputSettings=nil` 宣称通过。Apple 两端若教师路无声而改用其他路，也须记录并与界面说明一致。

### 3.2 性能比较必须拆开

| 指标 | 记录方式 |
| --- | --- |
| 纯媒体处理 | 固定本地输入，不下载、不复用已编码结果；分别记录两路解码、完整合成、整理、保存的实际边界 |
| 端到端 | 空的独立任务工作目录，从取列表/下载到成功提交目标；暂停时间另记，不能从总时长隐去 |
| 合成 FPS | 输出帧数 ÷ 合成墙钟时间；同时给出是否包含等输入、暂停、热降频或首次初始化 |
| 处理倍率 | 媒体时长 ÷ 处理墙钟时间；两路解码与只编码基准换算到同一媒体时间轴再比较，不直接比较分母不同的原始 FPS |
| 阶段耗时 | 标注下载和合成重叠；累计 `decodeMs/drawMs/encodeMs` 含等待，不等于硬件利用率，也不能直接相加当总时长 |
| 资源与环境 | 实际编解码器/GPU、供电、电量、温度、前后台、输入/输出字节、磁盘峰值与结束残留；内存/句柄/进程是否逐轮增长 |
| 网络 | 记录源字节量和下载耗时，缓存重放不计网络；网络变化不能作为编码算法提速证据。App 速度为分片处理后的平滑有效速率，不做网卡工具等值验收 |

有可重复收益且正确性、恢复和资源占用没有回退，才接受优化。9–10 分钟是 Android 目标，不是已达成绩，也不是四端必须共享的绝对时限。

### 5.2 操作顺序与保护条件

1. 读最新 `memory.md`、本文件、旧 Android 计划的状态更正，核实目标分支和工作区。
2. 先 `adb devices -l`，确认小米平板 8 Pro 的真实序列号、型号、Android 版本；其后每条 ADB 命令都用 `adb -s <确认的序列号>`。不凭 `device` 一词把模拟器当平板，记录中脱敏序列号。
3. 用显式 `-s` 读取 `dumpsys battery`、`dumpsys thermalservice`、`df -h /data /sdcard` 等，记录电量、温度/热状态、供电与可用空间；温度数据不存在时注明，不能填估计值。
4. 构建最新独立 `.playbacktest` debug 包；**当前普通 `:androidApp:assembleDebug` 默认 applicationId 仍是正式 App，不能直接安装它做隔离测试**。复用已有隔离构建脚本，或先补 debug 专用构建配置；安装前核对 APK applicationId、签名与版本。不卸载、不覆盖正式 App，不清除旧任务/账号/视频。确认后才 `adb -s <serial> install -r <isolated.apk>`。
5. 在独立目录复用既有真实课堂输入，保存输入指纹与档位。先做两路只解码、只编码、完整媒体处理的可比基准，再做从零下载端到端。明确哪些 debug 自测模式已有、哪些测量点缺失；只补采样与必要小修复，不假装尚未实现的基准已经存在。
6. 采集实际 decoder/encoder 名称、解码/GL/编码工作与等待、输出 FPS、队列等待、各段提交、快速整理是否命中/为何回退、最终复制与提交时间。记录取样周期，不能用首次看到阶段的时间冒充精确边界。
7. 按 F06 检查整节正确性，按 F07–F13 回归后台返回、页面重建、暂停/继续、强停重启、排队、取消、完成清理。软件或第二候选路径可先用短片验证，但报告必须注明其不代表整节性能。
8. 提交测量报告；设备不在身边、未授权 ADB、断连、空间/温度不满足时报告实际阻塞，保留已有数据，不以模拟器、桌面容器测试或理论值代替。

### 5.3 对照基线与 P0 交付

旧版固定课堂：约 1 小时 57 分，175564 视频帧、25 fps；不暂停端到端约 16 分 15 秒。下载约 8 分 14 秒，合成完成约 14 分 25 秒，整理约 1 分 31 秒，保存约 16 秒。下载与合成重叠，不能相加；原阶段观测有约 5 秒采样间隔，当前更精确测量不能假装旧数据同样精确。

报告必须包括：

- 提交、包标识、设备与热/供电环境、输入指纹、实际输出档位、缓存是否复用。
- 时间拆解、平均 FPS/处理倍率、实际编解码器、主要两个瓶颈和证据，不能把累计等待当硬件利用率。
- 快速整理/矩阵/候选回退的命中与正确性，异常及不可比项目。
- 帧数、PTS/DTS、AAC 样本哈希/数量/配置、首中尾和恢复边界、完整解码结果。
- 与旧版可比部分的提升、资源占用和恢复回归结果；端到端单列网络差异。
- 原始数据放 `.artifacts/android-perf/`；仓库可提交脱敏报告、独立测量工具与必要小修复，不提交真实账号数据或原视频。

P0 结束条件是取得可信测量与验收结论，不要求先达到 9–10 分钟；未测出的指标保留“未测”。

## 6. 后续第二步：Android P1 定向优化（PROMPT3）

前置条件：已完成上一节真机报告。先列最大两个耗时瓶颈，按预计收益、正确性风险、开发成本排序；没有报告时停留在测量阶段。

| 实测瓶颈 | 可研究方向 | 必守边界 |
| --- | --- | --- |
| 合成主循环 | 两路解码前瞻、GPU 提交、编码背压和不必要等待；必要时增加独立基准证实原因 | 保留 MediaCodec + OpenGL ES 架构；不靠降帧/丢帧、改档位提速，不破坏恢复时轴 |
| 整理 | 完善现有快速路径及回退；若确有收益再研究增量整理 | 样本、PTS/DTS、关键帧、配置与 AAC 一致；不重复开发已有 joiner |
| 保存 | 减少冗余 I/O、中间文件；研究支持条件下的 SAF 输出 | 未完成文件不能被当作最终成片；保持完整提交与中断/失败恢复语义，不假设所有提供者支持随机写或原子重命名 |
| 兼容/资源 | 实测启动失败、候选回退、热降频和中端限制 | 不只在高通上通过；新增跨芯片/串行回退须独立验证，帧数核对不能放宽 |
| 网络确成主瓶颈 | 最后再研究并发与学校限速 | 必须先证明合成已追上网络；不扩大媒体白名单，不破坏顺序交付与重试/断点 |

每轮只做一个主要优化：固定输入/设备/档位 → 测基线 → 修改 → 同条件复测 → 比较耗时/FPS/帧与音轨/磁盘/恢复 → 独立提交。若收益不明确或正确性退化，撤回本项修改，保留测量报告；不得覆盖用户其他改动。最后输出实测收益表、剩余瓶颈和下一阶段建议。

## 7. iOS / macOS：先补整节验收，再决定加速与恢复

### 7.1 iOS 待办

1. 在当前代码的真实 iPhone/iPad 上跑完整课堂：在线播放、预览、原生详情返回、两路全屏、下载→合成→保存→再打开；不能用旧 CI、短模拟器样本代表当前包。
2. 采集 AVFoundation 合成、网络、最终保存的时间拆解，检查内存、温度、磁盘和后台切换。先确定瓶颈，再决定是否改硬件处理路径。
3. iOS 26 的 BGContinuedProcessingTask：整次任务最多申请一次；系统进度活动生效时不叠加自绘活动，退回/结束/失败状态正确。iOS 18–25 与系统拒绝/撤销后台时间分别验收，不能承诺后台合成永不终止。
4. 当前没有与 Android/Windows 同等的任务队列跨进程恢复保证。先测清系统后台下载、回前台重试与 App 进程终止的区别，再设计持久化/授权句柄/恢复契约；未实现前 F08/F13 保持待补齐，不写“强停可恢复”。
5. 按第 3 节处理 AAC 重编码差距；检查源有声但音轨添加失败时是否会静默产出无声视频。
6. F10 用系统文件提供者、预览/分享/导出及合法持久访问实现可辨认保存位置与再次打开；不可随意复制 Windows 绝对路径/文件夹按钮。
7. 最新代码需 iOS 共享测试、宿主/扩展编译及最终 IPA 验证。模拟器按仓库要求签名，真机侧载包另核对签名、bundle 标识与后台任务标识；不因 CI 成功宣布真机安装/后台通过。

### 7.2 macOS 待办

1. 当前 DMG/源码实例在真实 Mac 跑同类整节，完成首中尾、完整解码、AAC 样本与时间轴检查；记录 helper 是否真实工作、硬件路径与速度。
2. 同输入区分纯媒体与网络端到端速度；先测再决定编码/整理优化，不直接照搬 Windows/Android 的数值和管线。
3. 验证三任务排队、取消、helper 异常、保存失败、工作目录清理及已保存视频保护。当前没有同等持久任务恢复接入，补齐前列明进程退出后的能力，不把内存任务页当恢复。
4. 关窗、Dock 重开、菜单退出、强制退出分别测；保持单源码实例，不触碰用户安装版，不用宽匹配结束进程。若退出时 helper 不受控，先修生命周期再谈加速。
5. 补可读保存位置与 NSWorkspace 等原生打开/定位入口、失效路径与中文/空格路径；当前共享完整路径按钮实现只在 Windows 打开，不代表 macOS 已具备。
6. 真实 Mac 检查窄/宽窗口、浅/深色、大字号、预览重试及 Safari 全屏；DMG 内 helper 与最终包代码一致。

## 8. 审查证据、回归和最终交付模板

所有 Gradle 命令在 `multiplatform/` 执行，使用 JDK21。共享行为变更至少运行 `:shared:desktopTest` 并编译受影响目标；Android `:androidApp:assembleDebug`；Windows `:windowsApp:windowsTest :windowsApp:compileKotlinWindows`；macOS 构建并启动；iOS 共享测试、签名模拟器/原生编译及所需真机流程。无法本地完成的目标明确交给后续 CI，未运行不写“仅 CI 已验证”。

Windows 硬件自测需本机既有 ffmpeg/ffprobe，显式启用 `BJTU_PLAYBACK_HARDWARE_ACCEPT=1` 后运行 `:windowsApp:windowsTest --tests '*WindowsPlaybackHardwareAcceptanceTest*'`。共享原生预览自测由 `BJTU_PLAYBACK_PREVIEW_ACCEPT=1` 开启，先编译 Windows helper，再运行 `:shared:desktopTest --tests '*WindowsPlaybackPreviewTest*'`。不开开关的跳过项不能当通过；ffmpeg 只作验证工具，不加入 App 运行依赖。

运行中不得重建其正在使用的共享 JAR。压力/界面测试使用固定运行副本，或先停实例再构建；构建干扰造成的类加载异常单列无效测试，不能冒充产品通过或回归。

每份平台报告至少填写：

| 字段 | 内容 |
| --- | --- |
| 版本 | 日期、分支/提交、是否带工作区修改、包构建标识、包/助手哈希 |
| 环境 | 设备/系统、GPU/实际编解码器、供电/温度/可用空间、网络及输入指纹 |
| 覆盖 | F01–F14 逐项：通过/失败/未测/经明确接受的例外；证据类别、命令、退出码、相对证据路径 |
| 媒体 | 尺寸/帧数/PTS/DTS、AAC 配置/数量/哈希、首中尾/恢复边界、实际播放与全解码 |
| 性能 | 本地媒体与网络端到端分列，阶段时间、FPS/倍率、峰值存储与异常 |
| 稳定性 | 至少三任务；Windows 同等级五轮短片压力；暂停/失败/取消/进程退出后的状态、输出及残留 |
| 限制 | 不能复现/设备不可用/未测硬件/系统后台限制；不得删除这些项使报告看起来全绿 |
| 结论 | 本平台是否可结项、需修复事项、后续兼容测试；独立于主干合入与正式发布 |

后续优先级：**Windows 已完成 → Android P0 真机测量 → Android P1 按证据优化 → iOS/macOS 整节与能力差距验收，再决定各自加速/恢复实现**。Apple 如具备设备可先做独立基线采集，但不以此跳过 Android 的测量门槛。
